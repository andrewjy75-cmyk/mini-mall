# Mini Mall 智能客服 RAG —— 优化过程与实验记录

> 本文记录的是**真实做过的调优过程**：每一步改了什么、为什么改、
> 改完效果如何、以及哪些改动其实没起到预期作用。
>
> 所有对比数据来自 `eval/run_eval.py` 的实际运行结果，
> 逐题明细（含模型原文和裁判理由）保存在 `eval/results/*.json` 中，可复核。

---

## 一、背景与目标

### 1.1 要解决的问题

电商客服的典型问答有两个特点：

1. **答案高度依赖平台自己的规则文档**。退换货期限、运费标准、保修范围，
   这些每家平台都不一样，模型预训练知识里根本没有，问了必然胡说。
2. **答错代价高**。客服说错一句「生鲜也能退」，用户就会照着做，
   后续的纠纷成本远高于开发这套系统的成本。

这两点决定了：**这不是一个"能用大模型聊天就行"的场景，而是一个必须压实
"答案有据可依"的场景**。所以整个优化过程的主线只有一个词——**抑制幻觉**。

### 1.2 技术选型

| 环节 | 选型 | 理由 | 放弃了什么 |
|---|---|---|---|
| 大模型 | DeepSeek（OpenAI 兼容接口） | 便宜、中文好、兼容协议意味着换厂商只改配置 | 没用本地大模型，因为 CPU 上 7B 模型响应要十几秒，客服场景不可接受 |
| 向量模型 | BAAI/bge-small-zh-v1.5（本地） | 免费、离线、数据不出本机 | 没用 API 向量，建索引时要把成百上千块全部向量化，调 API 是持续开销 |
| 向量库 | Chroma（本地文件持久化） | 零配置、不用起服务，是"可本地运行"的关键 | 百万级数据或多副本要换 Milvus/Qdrant，本项目几千块用不上 |
| 重排 | BAAI/bge-reranker-base | 交叉编码器，精度显著高于双塔 | 模型 1GB，首次下载慢，所以做了优雅降级 |
| 编排 | LangChain 生态 | 组件化、接口统一，方便做 A/B 和替换 | LangChain 抽象层有学习成本，某些地方不如直接写 SDK 直观 |

> **关于"为什么不全用 LangChain 现成组件"**：
> 上下文压缩这一环，LangChain 提供了 `EmbeddingsFilter` 和
> `ContextualCompressionRetriever`。评估后没有采用，原因是它的
> 压缩粒度是"整篇文档级"过滤，而我们需要的是**句子级**筛选
> （一块 600 字里可能只有两句话有用）。
> 所以最终的压缩器是自己实现的，但仍然实现了 LangChain 的
> `Embeddings` 接口，可以随时换回官方组件。
> 用生态不等于被生态绑死，该自己写的地方要自己写。

### 1.3 系统架构

整条链路分成两半，责任清晰：

```
【写入侧】离线，一次
  上传 → 解析(loader) → 切分(splitter) → 向量化(embedder) → 双写(Chroma + MySQL)

【查询侧】在线，每次提问
  提问 → 装载记忆 → 检索 → 重排 → 压缩 → 组装 Prompt → 生成 → 埋点
                     └──────── retriever 编排 ────────┘
```

分层依赖单向：`api → services → rag`。
`rag/` 不知道 FastAPI、不知道数据库，所以可以脱离 Web 单独跑评估——
这一点在后续做批量对比实验时省了非常多事。

## 二、检索链路设计

### 2.1 为什么必须分三段

检索不是"调一次向量库"就完了。最终采用的是三段式流水线：

```
┌──────────────┐   ┌───────────┐   ┌────────────┐
│ 向量召回      │ → │ 重排精排   │ → │ 上下文压缩  │
│ recall_k = 20│   │  → top_k  │   │ 只留相关句  │
│ 求"不漏"      │   │ 求"准"     │   │ 求"省"      │
└──────────────┘   └───────────┘   └────────────┘
```

每一段职责单一、可单独开关、可单独度量。**这个"可单独开关"是刻意设计的**：
如果揉成一个大函数，就只能做「全开 vs 全关」的对比，
得不出"重排到底贡献了多少"这种结论。

### 2.2 一个被忽略的关键参数：召回数 ≠ 最终数

这是本项目最早踩到的坑，也是**"做了重排却没效果"最常见的原因**。

最开始 `recall_k` 和 `top_k` 都设成 5。结果是：重排把同样那 5 条重新排了个序，
然后取全部 5 条——**等于什么都没做，纯粹浪费了一次模型推理**。

原因很直白：重排的作用是"从候选池里把正确答案捞到前面来"。
如果候选池本身就不包含正确答案（向量检索压根没召回它），
重排再强也变不出来。

改了参数之后：

```python
RETRIEVE_RECALL_K = 20   # 粗排多召回，保证"不漏"
RETRIEVE_TOP_K = 5       # 精排后只留 5 条，保证"准"且省 token
```

并且在 `retriever.py` 里加了一条判断：
**候选数不超过 top_k 时直接跳过重排**——没有选择空间的排序是无意义的，
这时候跳过能省下一次模型推理的延迟。

> 这类"不报错、只是悄悄变差"的问题最难发现。
> 如果只盯着"重排有没有开"，是永远查不出来的。

### 2.3 相似度阈值：宁可说不知道

```python
RETRIEVE_SCORE_THRESHOLD = 0.5
```

低于阈值的片段直接丢弃。这不是为了省 token，而是为了**少给模型递刀子**：
把一堆相关度只有 0.1 的内容塞进 Prompt，模型会把它们当成"可能的依据"，
硬凑出一个答案。相关性不足时说一句「没查到」，比给一个错误答案要好得多。

**这个值是实测调出来的，过程值得完整记录。** 最初按"看起来合理"设成 `0.25`，
跑起来发现它**等于没设**——拿知识库里根本没有答案的问题去检索，
最高分仍然有 0.445，照样一路送到模型面前。

于是写了个标定脚本 `scripts/probe_threshold.py`，用两组问题测真实分数：

- **A 组**：知识库里确实有答案的问题（希望被召回）
- **B 组**：知识库里根本没有答案的问题（希望被拦掉）

实测结果（`bge-small-zh-v1.5` + 余弦相似度）：

| 分组 | 最高相似度区间 |
|---|---|
| A 组（有答案，12 题） | **0.5537 ~ 0.6815** |
| B 组（没答案，12 题） | **0.2482 ~ 0.4830** |

两组之间有一道 **0.4830 ~ 0.5537 的空隙**，没有任何重叠——
说明单靠相似度就能把"有答案"和"没答案"分开。

所以阈值取在空隙里，`0.50`（空隙中点是 0.52）。
效果是：**12 个可回答问题全部保留，12 个不可回答问题全部拦截，两边都没误伤。**

> 这个"找空隙"的方法比拍脑袋定阈值可靠得多，而且它还能告一个重要的否定结论：
> **如果两组分数重叠了，说明阈值根本救不了这个场景**，
> 此时硬调只会顾此失彼（调高误杀能答的，调低放进无关的）。
> 那种情况下应该先去查根因：切分是不是把答案切散了、embedding 模型是不是太弱、
> 要不要上重排——而不是在阈值上反复试。
> 脚本里对这个情况有明确的分支处理和建议。

> ⚠️ **这个值强依赖于 embedding 模型**。换成别的模型，相似度整体分布会变
> （BGE 中文系列普遍偏高），**必须重新跑一次标定**，照搬数值没有意义。

这里还有个实现细节值得记录：**Chroma 返回的 `score` 是距离，不是相似度**，
而且距离越小越相关，方向和直觉相反。代码统一在 `vectorstore.py` 的出口处
做了 `similarity = 1 - distance` 的转换，让上层只面对一种语义。

> 这个坑如果搞反，现象是"检索出一堆最不相关的内容"，而且不报任何错。

## 三、Prompt 工程

### 3.1 先讲一个反直觉的结论

刚做这个项目时，直觉是「在 Prompt 里加一句『不要编造』就行了」。
实际测下来，**这句话几乎没有效果**。

真正起作用的是另外三件事：

| 做法 | 为什么有效 |
|---|---|
| **给一个体面的「我不知道」出口** | 模型编造，很多时候不是因为"想骗人"，而是因为它把"答不上来"当成了任务失败，于是硬凑一个答案。给一句标准话术，它就肯认输了 |
| **要求标注引用来源** | 一旦必须给出处，凭空编造的成本就变高了——要编就得连编号一起编 |
| **把资料编号给它，允许它指出冲突** | 不同文档的条款可能矛盾。允许它说"资料 2 和 3 说法不一致"，比逼它糅合成一个答案好 |

这三条正是 `v2` 和 `v3` 的核心改动。

### 3.2 版本演进

所有 Prompt 集中在 `rag/prompts.py`，每个版本是**独立、完整、可回退**的模板，
并强制标注「改了什么、为什么改」。

#### v1 —— 基线（故意保留朴素写法）

```
你是一个电商商城的客服助手，请回答用户的问题。

{context}
用户问题：{question}
请回答用户的问题。
```

已知问题：没说明资料里没有时该怎么办、不要求引用出处、角色设定太弱
（问退货会顺带讲一堆物流）。

#### v2 —— 加「不知道」出口 ★

相对 v1 **只改 Prompt**，其他一切不动，这样对比出来的差异才能归因到 Prompt。

新增的关键规则：

```
2. 如果资料不足以回答问题，直接回答："抱歉，我暂时没有查到相关信息，
   建议您联系人工客服核实。" 不要猜测，不要用你自己的知识补充。
```

另外补充了：规则 4 处理资料冲突、规则 5 屏蔽技术黑话
（不跟用户说"资料""上下文""检索"）。

#### v3 —— 强制标注依据 ★

在 v2 基础上增加：

```
6. 在回答的最后，单独一行写上「依据：」，列出你实际用到的资料编号，
   格式如：依据：[1][3]。只列真正用到的，不要罗列全部。
```

这一条同时打两个目的：
1. **给用户自查入口**：能点开原文核对，用户就不用盲信模型
2. **对模型形成隐性约束**：要写出编号，就得先在资料里找到依据

#### v4 —— 零温度

v4 的模板与 v3 完全相同，**唯一变量是把 `temperature` 从 0.1 降到 0**。

单独设一版是为了把「采样随机性对幻觉的贡献」隔离出来量化。
做对比实验最容易犯的错误就是一次改好几个变量，
那样即使效果变好，也说不清是谁的功劳。

### 3.3 引用编号的合法性校验

v3 要求模型标注依据。但如果模型在「资料里没找到」的情况下
**学着格式硬凑了一个编号**怎么办？

`rag_service.py` 里加了一个低成本探针：

```python
def parse_citations(answer): ...            # 抠出所有 [n]
def _resolve_citations(cited, sources):     # 校验 1 <= n <= len(sources)
```

如果模型写出了 `[7]`，而这次只提供了 3 条资料，就会被记成**非法引用**：

```python
logger.warning("模型引用了不存在的资料编号 %s（本次只提供了 %s 条），疑似硬凑依据", ...)
```

这类「格式正确、内容虚构」的回答是最危险的，因为它看起来最像真的。
非法引用率也作为一项指标进了评估脚本。

## 四、幻觉治理策略汇总

把上面的做法整理成一张表，方便对照：

| 策略 | 实现位置 | 作用机制 | 代价 |
|---|---|---|---|
| 相似度阈值过滤 | `retriever.py` | 不相关的内容不进 Prompt | 可能漏掉长尾相关片段 |
| 重排精排 | `reranker.py` | 把真正相关的提到前面 | 每次多约 300ms 推理 |
| 上下文压缩 | `compressor.py` | 减少噪音，避免注意力被稀释 | 可能切断限定条件（见下） |
| 「不知道」出口 | Prompt v2 | 消除模型"必须答点什么"的压力 | 无 |
| 强制标注依据 | Prompt v3 | 提高编造成本，提供自查入口 | 输出变长，延迟略增 |
| 低温采样 | Prompt v4 | 减少随机发挥 | 回答略显生硬 |
| 引用溯源返回前端 | `schemas/rag.py` | 让用户能核对原文 | 无 |
| 非法引用检测 | `rag_service.py` | 发现"硬凑依据"的信号 | 无 |

### 4.1 上下文压缩的副作用（一个必须说清的风险）

压缩用的是「句子级向量相关度筛选」，把和问题不相关的句子丢掉。
但这里有个**很隐蔽的陷阱**：

```
原文：「会员商品支持 7 天无理由退货。定制类商品除外。」
如果只保留第一句 → 回答"会员商品都能退"，把例外丢了。
```

这种「压缩导致的断章取义」**比不压缩更危险**，因为它看起来有出处。

代码里做了两处缓解：

1. **邻居句保留**：命中一句时，把它前后各一句也带上，保住上下文
2. **块数少时不压**：候选块少于 3 个时跳过压缩——
   `len(documents) < min_docs_to_compress` 时直接返回原样。
   理由是这时压缩省下的几百字，远不及它切断上下文的风险

> 优化不是无脑开开关。**知道什么时候不该优化**同样是优化能力的一部分。

### 4.2 分层记忆：不是"全都记住"

多轮对话的记忆设计成两层：

```
System Prompt（角色 + 铁律）        ← 每轮都带
长期记忆：summary（滚动摘要）        ← 每轮都带
短期记忆：最近 3 轮原话              ← 每轮都带
当前轮：检索资料 + 用户问题          ← 每轮变化
```

为什么不全部带上？
1. 上下文窗口有限，聊二十轮就爆
2. 就算塞得下，太多历史会让模型揪着很早之前的话题不放
3. 成本随轮数线性上涨

真正的问题是**怎么优雅地忘掉旧信息**。实现方式是滚动摘要 +
`ChatSession.summarized_count` 游标：

- 摘要覆盖 `[0, summarized_count)`，原文保留 `[summarized_count, 末尾]`
- 游标保证**幂等**：已摘要过的不会重复摘要（否则会"摘要的摘要"，越摘越糊）
- **原文一条都不删**，用户翻历史看到的是完整对话。
  摘要只是给模型看的压缩视图

> 把「给模型看的记忆」和「给用户看的历史」分开，是个重要的设计区分。
> 混在一起做的典型症状是：用户发现自己的话"被改写了"。

## 五、实验设计与结果

### 5.1 评估集设计

22 道题，分三类，**每类的考察目标完全不同**：

| 类别 | 数量 | 考察目标 | 判定标准 |
|---|---|---|---|
| 可回答 | 13 | 检索准不准 + 答得对不对 | 是否覆盖全部 key_points |
| **不可回答** | **6** | **★ 幻觉核心指标** | **有没有凭空给出具体信息** |
| 陷阱 | 3 | 能否正确处理限定条件 | 是否踩中易混淆点 |

**为什么"不可回答"这一类最重要？**

因为可回答的题，模型靠预训练知识也可能蒙对；
但不可回答的题（比如"客服电话是多少"），只要它敢给出一个具体号码，
就**一定是在编**。判定标准极其客观，没有解释空间。

所以本项目的**标题指标是「幻觉率」，而不是笼统的"准确率"**。

评估集里还埋了几个刻意设计的用例：

- **q06 / q07**：答案在 Word 表格里。答得出来才证明表格解析是有效的
- **q11**：必须同时命中《退换货政策》和《会员权益》两处并正确组合，
  单文档检索很难答对，**是验证重排价值的关键用例**
- **t03**：定制商品"不支持无理由退货"，但"质量问题退换货"是另一条规则。
  容易误答成"定制商品完全不能退换"——把两条规则混为一谈的典型错误

### 5.2 控制变量的实验矩阵

配置是**逐层叠加**的，每一步只动一个变量：

| 配置名 | Prompt | 重排 | 压缩 | 相对上一组，唯一的变量是 |
|---|---|---|---|---|
| v1-基线 | v1 | ✗ | ✗ | （对照组） |
| v2-防幻觉 | v2 | ✗ | ✗ | 仅 Prompt |
| v3-强制引用 | v3 | ✗ | ✗ | 仅 Prompt |
| v2+重排 | v2 | ✓ | ✗ | 仅重排 |
| v2+重排+压缩 | v2 | ✓ | ✓ | 仅压缩 |
| v4-零温度 | v4 | ✓ | ✓ | 仅 temperature |

### 5.3 实验结果

#### (1) 切分粒度对检索与重排的影响

用 `scripts/experiment_chunk.py` 跑的：固定其它所有变量，只改 `chunk_size`，
14 个带标准答案的问题，判定标准是「top1 片段是否包含答案关键词」。

| chunk_size | 块数 | 平均块长 | 向量检索 top1 | 重排后 top1 | 重排增益 |
|---|---|---|---|---|---|
| 200 | 38 | 156 字 | 12/14 | 11/14 | **−1** |
| 300 | 23 | 242 字 | 9/14 | 11/14 | +2 |
| **450** | 14 | 385 字 | 11/14 | **13/14** | +2 |
| 600 | 11 | 473 字 | 9/14 | 12/14 | +3 |

两个**反直觉**的结论：

1. **切得越碎不等于越好。** `chunk_size=200` 时向量检索本身最准（12/14），
   但重排之后反而掉到 11/14 —— 重排帮了倒忙。
   原因是块太小丢掉了上下文，重排模型失去了判断依据。

2. **块太大时重排的"增益"最大（+3），但绝对命中率上不去。**
   说明重排能纠正排序，却补不回"关键信息被一大段无关文字稀释"的损失。

最终取 `chunk_size=450`。

> ⚠️ **诚实说明**：14 道题的样本量偏小，450 与 600 的差距（13 vs 12）
> 在统计上未必显著。这里选 450 是"综合最优 + 不过度优化"的务实选择，
> 不是精确最优解。样本扩到 100 题以上才能给出置信区间。

#### (2) 相似度阈值标定

12 个"有答案" + 12 个"没答案"的问题，实测分数分布：

| 分组 | 最高相似度区间 |
|---|---|
| A 组（知识库里有答案） | 0.5537 ~ 0.6815 |
| B 组（知识库里没有答案） | 0.2482 ~ 0.4830 |

两组之间是一道 **0.4830 ~ 0.5537 的空隙**，没有重叠。
阈值取 0.50 落在缝隙内：可回答问题全部保留，不可回答问题全部拦截。

（详细推导见 §2.3。复现命令：`scripts/probe_threshold.py`）

#### (3) 重排的真实效果

除了上面那张命中率表，还有一组更能说明问题的观察。
把重排开启前后的候选分数打出来看：

```
问题「生鲜食品可以退货吗」，重排后三个候选块：
    0.7268  /  0.7257  /  0.6295
                ↑ 前两条只差 0.001
```

**重排确实执行了，但它给出的分数几乎没有区分度** ——
前两条差 0.001，这个"排序"和随机差不了多少。

原因在 §5.3(1) 里已经量化了：块太大时，一个 500 字的块里
和问题真正相关的可能只有一句话，重排模型看到的是
"95% 的内容都无关"，信号被稀释，自然给不出区分度。
把 `chunk_size` 从 600 降到 450 之后，这个问题明显缓解
（top1 命中从 9/14 提升到 11/14）。

> **这个发现比"重排提升了 X%"更有价值**：
> 它说明**重排的效果上限是由切分粒度决定的**。
> 切分没做好，重排再强也救不回来——
> 很多人抱怨"上了重排没效果"，根子往往在这里，
> 而不是重排模型选得不够好。

## 六、踩过的坑（按发现顺序）

这一节记录的是**实际排障过程**，不是从文档抄的注意事项。
每一个坑都真实消耗过时间。

### 6.1 国内网络下 huggingface.co 无法解析

首次加载 BGE 模型时直接失败。排查发现不是慢，而是 DNS 都解析不了：

```
https://huggingface.co  -> FAIL getaddrinfo failed
https://hf-mirror.com   -> 200
```

**处理**：配置 `HF_ENDPOINT=https://hf-mirror.com`。

但这里有个更隐蔽的点：`huggingface_hub` **只在被 import 的那一刻**
读取 `HF_ENDPOINT`。如果先 import 再设环境变量，是完全无效的。
所以最终是在 `core/config.py`（项目最早被导入的模块之一）末尾
把配置写回 `os.environ`，并在 `rag/embedder.py` 里把
`sentence_transformers` 的 import 延迟到函数内部，确保顺序正确。

### 6.2 Python 的字符串引号把代码写坏了

写评估集时，注释和字符串里混用了中英文引号，导致：

```python
"考"除外条款"这一类别名能否被召回",   # SyntaxError
```

**处理**：全文统一用中文引号「」而不是英文引号，
从根上避免和代码引号冲突。同时加了"逐文件语法检查"的习惯：

```powershell
Get-ChildItem -Recurse -Filter *.py | ForEach-Object {
    python -m py_compile $_.FullName
}
```

### 6.3 上传文件不能用用户提供的文件名拼路径

如果直接 `UPLOAD_DIR / file.filename`，用户可以把文件名设成
`../../../windows/system32/xxx`，直接写到项目外面——路径穿越攻击。

**处理**：用自己生成的 `doc_id` 当文件名（`{doc_id}{suffix}`），
原始文件名只存数据库当展示用，**绝不参与任何路径拼接**。
顺带也解决了同名文件互相覆盖的问题。

### 6.4 Word 的表格不在 `doc.paragraphs` 里

`python-docx` 的 `doc.paragraphs` **不包含表格中的文字**。
而运费标准、配送时效这些关键信息恰恰都在表格里。
只读 paragraphs 会**静默丢掉最重要的那部分内容**。

**处理**：遍历 `doc.element.body` 按真实顺序处理段落和表格，
并把表格转成 Markdown（保留行列结构）。
转 Markdown 而不是拼成一行文字，是因为拼成
「商品名 价格 库存」这种串，模型分不清哪是列名，回答时会串行。

### 6.5 PDF 的换行是"视觉换行"

PDF 提取出来是这样的：

```
退换货政策如下：
商品签收后 7 天内
可无理由退货。
```

这些 `\n` 是排版需要，不是句子结束。直接连起来会把一句话拆散，
影响切分和向量化的语义完整性。

**处理**：实现 `_join_wrapped_lines()`——当上一行末尾和下一行开头
都是中文字符时，判定为硬换行，接起来。同时保留空行（段落边界是切分的依据）。

### 6.6 扫描版 PDF 会静默入库空文档

`pypdf` 对扫描件提取出的是空字符串。如果不管，
就会往知识库里塞一堆空文档，检索永远命中不了，
**而文档列表里看起来是"成功的"**，排查起来极其痛苦。

**处理**：提取完做空内容检查，直接报错：

> 「未能从该 PDF 中提取到任何文字。如果它是扫描件或纯图片 PDF，
> 需要先做 OCR 识别——本项目暂未内置 OCR。」

宁可明确失败，也不要静默入库垃圾数据。

### 6.7 换 embedding 模型后旧数据不能继续用

旧向量是用旧模型算的，新向量是另一个模型算的。
两者**不同源**，在同一个空间里算距离是没有意义的，
检索结果会变得莫名其妙（而且不报错）。

**处理**：实现了 `POST /api/knowledge/docs/{id}/rebuild`，
用当前配置重新解析、切分、向量化。
这是"可维护性"的具体体现——没有重建能力，
切分参数和向量模型就永远定死在第一版，再也改不动了。

### 6.8 压缩模块把两套下标搞混了

**现象**：多轮问答时接口突然返回 500，日志里是

```
File "rag/compressor.py", line 173, in compress
    kept_text = "".join(sentences[i] for i in sorted(expanded))
IndexError: list index out of range
```

**排查**：越界的边界检查明明是写了的：

```python
for i in keep_indices:
    if i - 1 >= 0:      expanded.add(i - 1)
    if i + 1 < total:   expanded.add(i + 1)
```

`i` 不会越界，那问题只能在 `keep_indices` 本身。

回头看挑选句子的那段代码：

```python
# 挑选时：i 是 all_sentences（所有文档摊平后）里的【全局下标】
doc_candidates = [(i, s) for i, s in scored if index_map[i][0] == doc_idx]
selected[doc_idx] = sorted(i for i, _ in keep)          # ← 存了全局下标

# 使用时：却拿它去索引【单篇文档】的句子列表
sentences = per_doc_sentences[doc_idx]
sentences[i]                                            # ← 局部下标才合法
```

**两套下标空间不一致**：存的是摊平后的全局下标，用的地方却当它是文档内下标。

- 文档 0 的句子正好排在全局列表最前面，两套下标**恰好对齐**，
  所以单文档测试、或者只看第一个文档时，一切正常；
- 从文档 1 开始，全局下标必然超出该文档的句子总数，直接越界。

这就是为什么它**只在多文档、且恰好走到压缩路径时才炸**——
单测跑第一个文档永远是绿的。

**修复**：存的时候就换算成文档内的局部下标：

```python
selected[doc_idx] = sorted(index_map[i][1] for i, _ in keep)
```

**顺带加的防御**：这个位置是"一个下标算错就让整个接口返回 500"的关键点，
所以又加了一道 `0 <= i < total` 过滤，真越界时打 warning 而不是崩。
少拼一句话可以接受，把接口打挂不行。

> **教训**：只要代码里同时存在"全局下标"和"局部下标"，
> 就必须在命名上把它们区分开（`global_idx` / `local_idx`），
> 并且在跨函数传递时明确换算。混用两套下标空间的 bug，
> 特征就是"在特定数据组合下才爆炸"，极难复现和定位。

### 6.9 异常处理"漏盖了一块"

**现象**：没配 `LLM_API_KEY` 时提问，返回的是

```json
{"code": 500, "message": "服务器开小差了，请稍后再试"}
```

但原因其实非常明确（key 没填），提示却变成了"服务器坏了"。
更糟的是流式接口，直接报连接被对端中断。

**排查**：`get_llm()` 里明明有检查：

```python
if not settings.llm_configured:
    raise LLMNotConfiguredError("还没有配置大模型 API Key……")
```

异常抛得没问题，问题在**调用处没有把它盖住**：

```python
llm = get_llm(temperature=...)      # ← 在 try 外面！
try:
    response = await llm.ainvoke(messages)
except Exception as exc:
    ...
```

`get_llm()` 这一行在 `try` 之外，
所以它抛的异常直接冒到全局兜底处理器，变成了"服务器开小差了"。

**修复**：

1. 把 `get_llm()` 移进 `try`（`ask` 和 `ask_stream` 两处都有这个问题）；
2. 在 `main.py` 单独注册 `LLMError` 的处理器，把"人话版"消息直接透传，
   code 用 503 而不是 500 —— 语义上是"依赖的外部服务不可用"，
   不是"服务器崩了"；
3. `friendly_error()` 里加一条短路：如果异常本来就是 `LLMError`，
   直接返回它的消息，不要再套一层"调用大模型失败（XXX）"把干净的提示弄脏。

> 关于处理器为什么放在 `main.py` 而不是 `core/exception.py`：
> 后者属于最底层，不能反过来 `import rag`，否则分层就乱了。
> `main.py` 在最外层，两边都能依赖，放这里不破坏任何约束。

> **教训**：写 `try` 的时候要问一句——**可能出错的那一行，在 `try` 里面吗？**
> 这类 bug 不是"没做异常处理"，而是"没盖住"。
> 排查时看到一个过于笼统的错误提示（"服务器开小差了"），
> 基本上就意味着有明确的异常被漏到了兜底分支。

### 6.10 ORM 对象少刷新一个字段，接口就 500

**现象**：上传文档接口返回"服务器开小差了"，
但去查数据库——文档、切片、向量**全都写进去了**，一条不少。
也就是说"活儿干完了，但回话的时候摔了"。

**排查**：异常是

```
pydantic_core.ValidationError: 1 validation error for KnowledgeDocOut
created_at
  Error extracting attribute: MissingGreenlet: greenlet_spawn has not been called
```

根因是 `created_at` 这类字段用的是数据库端默认值：

```python
created_at: Mapped[datetime] = mapped_column(server_default=func.now())
```

**值是数据库生成的，插入后 ORM 并不知道它等于多少。**
于是等接口层做 `model_validate(doc)` 去读 `doc.created_at` 时，
SQLAlchemy 会临时发一次查询去补这个字段 —— 这是"隐式惰性加载"，
而**异步 Session 里不允许这种同步 IO**，直接抛 `MissingGreenlet`。

**修复**：在写完之后显式刷新一次：

```python
await self.db.commit()
await self.db.refresh(doc)      # 把数据库生成的 created_at / updated_at 取回来
```

`chat_service.append_message()` 里的 `ChatMessage` 有同样的问题，一并补上。

> **教训**：异步 ORM 下，凡是**由数据库生成**的字段
>（`server_default`、自增、触发器写入的列），
> 提交之后要么显式 `refresh()`，要么在建表时就改用应用端默认值
>（`default=datetime.now`）。
> 这个坑的迷惑性在于：**数据是对的，只有响应是错的**，
> 很容易误判成"入库失败"而去查数据库。

## 七、已知限制与后续计划

### 7.1 当前限制

| 限制 | 影响 | 改进方向 | 优先级 |
|---|---|---|---|
| 文档同步处理 | 大文件请求等待久 | 后台队列 + 状态轮询 | 高 |
| 不支持扫描版 PDF | 扫描件无法入库 | 接入 PaddleOCR / RapidOCR | 中 |
| 评估集仅 22 题 | 统计置信区间宽 | 扩到 100+ 题并入 CI | 中 |
| 重排模型 1GB | 首次使用下载慢 | 换更小的蒸馏重排模型 | 低 |
| 未做多租户隔离 | 知识库全局共享 | 加 tenant_id 字段 | 上线前必做 |
| 上传接口未鉴权 | 任何人可写知识库 | 加管理员权限校验 | 上线前必做 |

### 7.2 有意不做的

- **没有引入 RAGAS 等评估框架**：当前 22 题、单轮问答的规模，
  自建评估脚本（约 300 行）已经够用，接入框架的收益不足以抵消学习成本。
  题目规模上百后再考虑。
- **没有做查询改写（Query Rewriting）**：多轮对话里的指代消解
  （"那它多少钱"）目前靠对话历史兜住。查询改写能进一步改善，
  但会引入一次额外 LLM 调用，延迟翻倍。属于待验证的优化项。

## 八、小结

这个项目里真正有效的优化，按贡献度排序大致是：

1. **给模型一个「我不知道」的出口** —— 改动最小，效果最明显
2. **让召回数远大于最终数** —— 重排能不能起作用的前提
3. **相似度阈值过滤** —— 不相关的内容根本不进 Prompt
4. **表格与换行的正确解析** —— 解析是质量天花板，这里丢的信息后面补不回来
5. **强制标注依据 + 引用溯源** —— 让用户能自查，而不是盲信

反而是一些"听起来高级"的手段，收益低于预期：
- 单纯加一句"不要编造"（几乎无效）
- 在候选池不够大时开启重排（纯浪费推理）
- 在候选块很少时做上下文压缩（风险大于收益）

**结论**：RAG 的效果瓶颈，大多数时候不在"用了多先进的模型"，
而在**检索质量、解析质量、以及 Prompt 里有没有给模型留退路**。
